# 11 — Decision record

The decisions that produced this spec, recorded like Phase I's D1–D10 so the reasoning survives
the conversation that created it. Each is ratified (author + GPT review).

| # | Decision | Rationale |
|---|---|---|
| **D1** | **Phase II is an evidence-and-attribution system, not an adapter package.** The report schema (§06) + attribution taxonomy (§05) are the spine; adapters/lanes are populators. | Centering on adapters risks "three clever vendor integrations" that never defined what conformance means. The durable asset is the measurement language. |
| **D2** | **Model-agnostic core; pluggable `ModelConsumerAdapter`s.** Generalize the existing `ModelAdapter`; browser-native agent is a *future* adapter, not the centre. | Only a normalize-once/route-through-adapters shape lets the *same* surface be compared across GPT/Claude/Gemini. |
| **D3** | **Same-surface invariant + one adapter-independent execution bridge.** Adapters decide *what* to call; the bridge executes against the *same* surface for all. | Without it, a difference could be model, translation, consumer logic, or plumbing — attribution becomes impossible. |
| **D4** | **N consumers from day one; Phase II is not complete until GPT+Claude+Gemini run one surface and divergence reporting works.** | The distinguishing feature (cross-consumer divergence) must actually arrive, not be deferred into a "conformance" package that only ever tested one path. |
| **D5** | **Versioned machine-readable report + human rendering, treated as a public contract** and the seed of Phase IV qualification. | A stable atom lets Phase IV aggregate rather than redefine. |
| **D6** | **Split-lane v0.1:** automated reference-runtime lane + real Chrome/WebMCP acceptance lane, clearly labeled; shim results never presented as browser conformance. | WebMCP is flag-gated Chrome-only today; honesty about what a shim proves is non-negotiable. Full real matrix is Phase VI. |
| **D7** | **`@zioladev/provider-conformance`, standalone public Apache-2.0.** Local/single-machine open; hosted recurring/browser/model matrix later. | Keeps core function genuinely open; puts the commercial center where the recurring cost is. |
| **D8** | **Mandatory attribution across nine categories; a consumer-side failure is never provider nonconformance.** Provider grade computed only from the four provider-owned categories. | Fault isolation is what makes "conformance" a serious word and the report actionable. |
| **D9** | **Divergence has a precise predicate** — same provider def + same task → materially different *observable* outcome — and is **descriptive, not automatically failure** (behavioral / outcome / conformance). | Prevents the harness from degrading into a model-consistency checker; *different ≠ wrong*. |
| **D10** | **Conformance ≠ interoperability.** Provider conformance is a prerequisite for interoperability, not interoperability itself; no journey/itinerary state in this package. | Stops Phase III from leaking backward into Phase II. |
| **D11** | **Observed facts vs. derived judgments are stored separately.** Verdicts are re-computable from raw observations; a re-score never re-runs. | Interpretation rules will change; the evidence must outlive any one interpretation. |
| **D12** | **Stable provenance identifiers** (`caseId`, `taskId`, `providerDefHash`, `toolSurfaceHash`, `adapterId`/`adapterVersion`, `modelId`, `runtimeId`, `browserVersion`, `modelParams`). | So "same test case, different model/runtime" is a fact, not a philosophical aspiration. |
| **D13** | **First-class outcome vocabulary; no collapsing into `not_executed`.** `executed`, `blocked_by_provider_contract`, `clarification`, `no_tool_selected`, `malformed_arguments`, `adapter_error`, `runtime_error`, `transport_error`, `execution_bridge_error`, `provider_error`. | "No provider call" means at least seven different things; collapsing them makes the report useless. |
| **D14** | **Frozen fixture discipline.** Task, provider def, tool surface, provider state, declared allowable outcomes, model params, runtime are pinned + hashed before a case runs. | If "same task" isn't actually the same, every verdict and divergence claim is unfounded. |
| **D15** | **Model narration excluded from core conformance scoring.** Captured as optional evidence only. | Keeps the judge-dependent language layer permanently out of the scoring path. |
| **D16** | **Clean-room extraction — total independence.** No runtime dep, dev dep, type-only import, generated artifact, fixture, or source path from `@selvage/*` (or the Refraktor extension) may be required to build, test, or execute the package. A CI check asserts the absence of any `@selvage` import/path. Selvage governance stays out entirely (Phase V, optional module on top). | Keeps proprietary governance logic from leaking into open tooling; the package must stand alone so the architecture tells the truth — conformance is not a thin public wrapper around proprietary enforcement. |
| **D17** | **`plan()` never executes — an architectural invariant, not an interface preference.** Adapters decide; the one common bridge executes. The type is renamed `ModelConsumerAdapter` (past the `@selvage/core` `ConsumerAdapter` collision). | If any adapter could execute, vendor paths would hide different execution behavior and the attribution taxonomy would collapse into "something went weird over there." |
| **D18** | **Golden report fixtures with authored, known-correct attribution**, locked in 2A, gating CI. Cover every provider-owned category + a divergence-≠-failure case. | Every future change to the report engine must preserve the attribution truths; without them Phase II becomes philosophically unstable as adapters accumulate. |
| **D19** | **Report identity includes the report generator** (`reportGenerator` / `reportGeneratorVersion`), and field names are deliberately literal, never cute. | A grade is only meaningful paired with the engine that computed it; the report is a durable contract Phase IV/VI build on — a clever name today is a migration tomorrow. |

| **D20** | **Task conformance is enforced against a frozen allowable set.** A clean terminal response outside the case's a-priori allowable set is a **consumer-side** fault (fabricated execution → `model_arguments`; illegitimate clarify/no-action → `model_tool_selection`), never provider-owned. "Execute with a default" is legitimate **only if the provider declares one.** Reuses existing categories → no report-version bump. | Without it, an underspecified task's fabrication is silently PASS. The rubric is frozen *before* models run; model behavior is observation, not ground truth. |
| **D21** | **The proof stack keeps its lanes separate.** A real model network path validated through the pipeline is a `reference-runtime/1` proof — **not** a real Chrome/WebMCP proof. The Chrome/WebMCP lane stays a distinct, later proof (2C). | Conflating "a real model ran" with "it ran against real WebMCP in Chrome" would overclaim. The clean stack: 2A instrument validation · 2B(det) adapter semantics · 2B(live) real model path on the reference lane · ambiguous-task divergence · 2C three-way + real Chrome lane. |

| **D22** | **Divergence is scored at two levels: representational vs. behavioral.** Observed outcomes (`clarification`, `no_tool_selected`, `executed`, …) stay distinct; a higher-order **action disposition** (`acted` / `deferred` / `failed`) drives behavioral divergence. Two paths that both `deferred` are not behaviorally divergent even when their labels differ. Text-only model output is **never** upgraded to `clarification` without a separate judge layer. | A live run showed a scripted `clarification` vs. a real model's `no_tool_selected` — same practical result, different label. The disposition layer keeps the raw outcome precise while preventing the divergence logic from inventing significance where there is none. `different ≠ wrong`; here, different isn't even behaviorally different. |

| **D23** | **`inspected` is a distinct disposition; attribution is effect-aware and first-failing-layer.** A read-only execution → `inspected` (not `acted`); state-changing → `acted`; no execution → `deferred`; failure → `failed`. An out-of-allowable execution attributes by where the first mismatch enters: a read / non-execution outside allowable → `model_tool_selection` ("selected an exploratory read outside allowable terminal outcomes"); a state-changing execution whose supplied required value violates the frozen task → `model_arguments`. No "fabricated input" wording where nothing was fabricated. The frozen rubric is **not** relaxed to bless the read. | A live run had Claude defer (ask the user) and GPT inspect (run `find_item`) on the same task — a real cross-ecosystem strategy difference the report must preserve without exaggerating it into a failure or blaming the provider. Whether a read is valid *trajectory* progress is Phase III (journeys), never Phase II (single decisions). |

| **D24** | **The Chrome/WebMCP lane is the next phase gate, and the lane changes but the measurement language does not.** Chrome must be *another lane populating `provider-conformance-report/1`* — not a reason to redesign the schema. Acceptance requires live registration/discovery/execution (read + state-changing) via real `document.modelContext` with `RegisteredTool` handles, preserved evidence, captured `browserVersion`, comparability-without-conflation vs. the reference lane, and **one intentionally browser-owned failure** proving `Browser Runtime: FAIL / Provider: PASS`. Explicitly not Phase III (no journeys). | If the schema must change to fit Chrome, the abstraction was incomplete; if Chrome slots in as a lane, that is the proof. Real models (done) + real WebMCP runtime (this) are the two independent dimensions that make Phase II genuinely real. See §14. |

## Phase III — trajectory layer (report contract `/2`)

Ratified (author + GPT). Phase II measures a single **decision**; Phase III measures a
**trajectory** — an ordered `inspect → decide → commit` sequence with step-to-step state
transfer, toward a terminal state. See §15.

| # | Decision | Rationale |
|---|---|---|
| **D25** | **A trajectory is an ordered sequence of independently attributable decisions/executions; the trajectory layer must NOT erase Phase II attribution.** Every step keeps its own `evaluatePath` evidence; the trajectory judgment (ordering, state propagation, terminal, orchestration) sits *above* the steps, never in place of them. | Collapsing a journey into one PASS/FAIL would throw away exactly the fault isolation Phase II exists to provide. The step tree is the record; the trajectory verdict is a layer on top. |
| **D26** | **`trajectory_orchestration` is a new attribution owner (bumping the contract to `/2`).** It owns sequencing faults — valid steps in an invalid order, failure to carry a prior output forward, skipping a prerequisite, committing before required inspection, wrong transition, continuing past termination. It is consumer/orchestrator-owned and **never** alters the provider grade. **Discipline:** attribute here *only* when each individual step was itself valid but the journey logic was wrong; a wrong tool *inside* a step stays `model_tool_selection`. | Trajectories change the semantic meaning of the contract (ordered steps, state transfer, terminal). Forcing sequencing faults into existing buckets would misattribute them; a new owner keeps them honest without touching the provider. |
| **D27** | **`/2` is a distinct contract, not a superset field on `/1`.** `/1` stays the single-decision report; `/2` is trajectory-aware. A tool_call outside the journey's sanctioned tool set is a **step-level** `model_tool_selection` fault (the model chose a tool the task never authorized), detected before execution. | Keeping the two report versions separate is cleaner forever than overloading `/1` with optional trajectory fields; the sanctioned-set check gives "wrong tool" a clean home that is not orchestration. |
| **D28** | **Freeze terminal states + invariants, not canonical paths.** A trajectory fixture pins initial state, required/forbidden terminal states, semantically necessary invariants, allowed step types, and any hard ordering — but **not** one required route. Constrain what must be *true*, not *how* the model gets there. | Requiring a canonical path would punish legitimate model strategy differences. `inspect menu → inspect item → commit` and `inspect item → commit` both conform if the invariants hold. |
| **D29** | **Trajectory divergence is three orthogonal flags:** `pathDifference` (routes differ), `terminalStateDifference` (end states differ), `trajectoryConformanceDifference` (one conforms, another doesn't). Same terminal state via different valid paths is **path difference, not behavioral failure** — the Phase II law `different ≠ wrong` lifted to journeys. Meaningful divergence is a different terminal state, a violated invariant, a failure to terminate, or one succeeding where another cannot. | Two models taking different but valid routes to the same result is exactly the interoperability observation the system exists to make — and exactly the thing a naive comparator would wrongly flag as failure. |
| **D30** | **3A is single-provider, multi-step, reference-lane only; and it is not "done" until a golden sequencing fault attributes to `trajectory_orchestration` without altering provider grade.** Locked non-goals: no live-browser trajectories, no retry/error-recovery engine, no multi-provider handoff, **no Selvage/authorization** in 3A. Golden set (T1–T6): happy PASS; commit-before-inspect → orchestration; output-not-forwarded → orchestration; wrong-tool → `model_tool_selection`; bad evidence → provider-owned; two valid routes → path difference only. Later: 3B multi-provider handoff · 3C multi-model over one trajectory · then real Chrome. | Prove the *instrument* before increasing dimensionality — the same discipline that made Phase II real. Proving only the happy journey would not prove the new attribution category actually works. |

## Phase III / 3B — multi-provider trajectories (grounded by the TreeFrog/Refraktor dig)

Ratified (author + GPT) after a clean-room extraction inventory against the production TreeFrog/
Refraktor code. The dig's headline: TreeFrog had the skeleton (an itinerary + declared-vs-actual
conformance) but **production never had true portable state propagation between steps** — so
lineage-bearing carried state becomes a first-class interoperability primitive. 3B is single
consumer, multiple providers, reference lane. See §16.

| # | Decision | Rationale |
|---|---|---|
| **D31** | **Provider identity splits into `origin` and `toolEndpoint`, never collapsed.** `origin` is the security/identity boundary; `toolEndpoint` is the exact tool-bearing location. A trajectory step names `{id, origin, toolEndpoint?}`. | Production taught us the hard way: landing page ≠ tool-bearing page (fieldbook §2.2). Collapsing them into one URL loses the distinction that makes cross-origin discovery reliable. |
| **D32** | **Cross-provider carried state is provenance-bearing, and is the centerpiece of 3B.** A `CarriedValue` is `{key, value, producedBy:{stepId, providerId, toolName}, evidenceRef?}`. No flat, un-attributed value merge. A later step may reference a prior key to source an input. | The single most important finding of the dig: production carried the *plan* forward but not the *outputs*. Lineage ("which provider/tool produced this, was it observed or invented?") is what makes transaction assurance possible later — flat state destroys it. |
| **D33** | **3B golden set proves the new abstraction, not breadth.** Fixtures: successful cross-provider carry; missing required carried value → `trajectory_orchestration`; downstream continuation after prerequisite failure → orchestration; iterated-but-terminal-not-attained → orchestration; inspected-but-required-commit-never-occurred → orchestration; plus provider-fault isolation. **Deferred:** fabrication/self-verification (FX2) and asking-instead-of-committing (FX3) to 3C (they are richest across models); stale-carried-term (FX4) held back so Phase III does not drift into Selvage/assurance thinking too early. | Prove cross-provider state mechanics first; expand the failure library later. Pulling term-consistency in now would brush against authorization semantics prematurely. |
| **D34** | **A provider transition and surface-readiness are trajectory REQUIREMENTS; the mechanism is lane-owned.** The engine models `provider_transition → surface_ready → discovery_complete` and records it; HOW readiness happens (instant on the reference lane; navigate → bounded poll → nudge on Chrome) lives in the lane's `SurfaceResolver`, never in the engine. | The trajectory contract owns *the requirement*; the lane owns *the plumbing*. Chrome polling logic in the trajectory engine would re-entangle contract and mechanism — the exact mistake the Chrome-lane work (D24) avoided. |
| **D35** | **The Selvage wall, phrased exactly.** Phase III MAY observe that a commit occurred, failed, or used stale/inconsistent carried state, and MAY report that fact. It MAY NOT decide whether a commit is authorized to proceed — it never intercepts, gates, binds, or blocks. Orchestration can say "you committed before inspecting"; it can never say "therefore I prevented the commit." | Measurement observes; governance intervenes; they never touch. The exclusion boundary runs through `wrapExecuteTool` (dig, bucket 4). Keep it immaculate: the open package imports nothing from `@selvage/*`. |
| **D36** | **Model memory is never authoritative trajectory state.** The model may receive carried state as context and reason over it, but the authoritative carried state is built by the engine from OBSERVED EXECUTION EVIDENCE only. A step's `bindings` are a claim, verified against that authoritative state — never trusted as truth. | Production taught this the hard way: a model re-emitted a fabricated tool-result as if real (dig, FX2). If the model's assertion could define state, the whole attribution edifice is forgeable. |
| **D37** | **Completing the loop is not completing the trajectory.** Terminal state is decided by the frozen terminal predicate (did the required commits actually occur?), never by "all planned steps were iterated." | Production granted `ok:true`/"done" when a leg produced only a summary; `completed = steps.every(executionAttained)` was a *separate* truth (dig, §10). Iterating the plan and attaining the outcome are different facts, and only the second is completion. |

## Phase III / 3C — cross-model trajectory comparison

Ratified (author + GPT). The richest Phase III question: given the SAME frozen multi-provider spec,
starting state, provider surfaces, carried-state model, common bridge, and terminal rules, do
Claude, GPT, and Gemini each reach an allowable terminal state, and where do their trajectories
diverge? Single lane (reference), single frozen spec, production-derived adapters. See §17.

| # | Decision | Rationale |
|---|---|---|
| **D38** | **Trajectory comparison is based on OBSERVED EXECUTIONS and AUTHORITATIVE CARRIED STATE, never on the model's narration of progress.** A step is attained only when the common bridge actually executed the provider tool; a model that says "done" without executing has attained nothing. | FX2 turned into architecture (and the natural extension of D36). Production had a model re-emit a fabricated result as real; if narration could define attainment, cross-model comparison would compare stories, not facts. |
| **D39** | **Ownership refinement: a model's clean decline of a required commit is a MODEL fault (`model_tool_selection`), not orchestration.** When the model asks, inspects, or narrates instead of performing a required state-changing commit, the trajectory *records* terminal-not-attained, but the fault is attributed to the model — because a correct runtime does NOT advance on the model's word. Orchestration owns the RUNTIME mishandling case (a runtime that believes the narration and advances). Rule: **model errs → model layer; runtime mishandles → orchestration.** (This reclassifies the 3B terminal-non-attainment fixtures G3B-4/G3B-5 from orchestration to `model_tool_selection`.) | "Where does the first incorrect decision enter?" A model choosing not to commit is a decision fault; blaming orchestration would misattribute a model problem to the sequencing layer. Our runtime never advances on narration (D38), so terminal non-attainment from a clean decline is always the model's. |
| **D40** | **Different path is not failure — lifted to cross-model trajectories.** Two models that take different but valid routes to the same allowable terminal state, preserving carried state and satisfying every invariant, are BOTH conformant: path difference, not failure. Meaningful divergence is a different terminal state, a violated invariant, a failure to terminate, or one model conforming where another cannot. **3C success is convergence:** production-derived Claude/GPT/Gemini adapters traverse the same frozen multi-provider trajectory, with authoritative carried state and one common bridge, and reach the same allowable terminal state — path differences preserved, never treated as failure. | The Phase II law (§07) raised to trajectories. The system's job is to tell the truth — if all three converge, that is the valuable result; if one breaks the trajectory, that is valuable too. Never manufacture divergence for drama. |
| **D41** | **The 3C live gate is cloud-only and evidence-complete.** The live three-model run is a `workflow_dispatch` GitHub Action using repository secrets for the three keys — no local terminal, IDE, or environment. The fixture (`crossModelJourneySpec`) is committed BEFORE execution and never edited after observing behavior; the report + raw evidence upload as a workflow artifact. Before the live run, `history` + `carried` are threaded into each production-derived adapter in that vendor's tool-call/tool-result format, keeping the same frozen spec, common bridge, and terminal predicates. **Each model's RAW response is preserved at EVERY trajectory step, not merely the final one.** This is the 3C live acceptance gate — not a new phase. | The user is cloud-only, exactly as the 2C three-way and Chrome-lane acceptances were. Threading history is what lets a real model traverse a multi-step trajectory at all; freezing the fixture first keeps the rubric honest; and Phase II taught us that keeping only the final response loses the evidence that explains where a trajectory actually broke. |

## Phase III — the Chrome/WebMCP acceptance gate (§18)

| # | Decision | Rationale |
|---|---|---|
| **D42** | **The real Chrome/WebMCP acceptance uses Refraktor as the privileged browser host/transport, not a second extension or a headless harness — and interop-runtime stays the brain.** interop-runtime defines a `BrowserHost` port (navigate / list / execute one call at a time) and drives it via a Chrome-lane `SurfaceResolver`; Refraktor implements the port over its existing low-level bridge (`navigateAndDiscover`, `executeToolOnPage`, `unwrapResult`). interop-runtime imports nothing from Refraktor; Refraktor's **legacy itinerary/orchestration (`buildItinerary`/`verifyJourney`/`create_itinerary`/`fulfillStep`) is NOT used** for the run. This is the final Phase III gate, not a product dependency; headless Chromium remains Phase VI. | The cross-origin hop needs browser privilege that survives navigation — Refraktor already has it. Building a second host would be waste; letting Refraktor's old orchestration drive would measure the old system, not the new one. The port's shape (no plan/sequence method) makes "new brain, existing arms and legs" structurally enforced: the host is handed one navigation/discovery/execution at a time and never decides the journey. |

## Ratified requirements folded in from review

- **Attribution categories:** `provider_definition`, `provider_runtime`, `browser_runtime`,
  `consumer_adapter`, `model_tool_selection`, `model_arguments`, `execution_bridge`,
  `provider_execution`, `evidence_contract` (§05).
- **Divergence classes:** behavioral / outcome / conformance (§07).
- **The target report sentence** ("Provider: PASS … Consumer execution bridge: FAIL, invalid
  RegisteredTool invocation") is the acceptance bar for the report's expressiveness (§05, §06).
